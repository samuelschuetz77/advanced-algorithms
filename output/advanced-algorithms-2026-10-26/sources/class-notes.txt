HALVING ALGORITHM — RECURSION TREES AND RUNTIME

Given:

def halving(n):
    if n <= 1:
        return 1
    return 2 * halving(n // 2) + 1


============================================================
1. WHAT DOES log₂(n) MEAN?
============================================================

The easiest way to think about a logarithm:

log₂(n) = "How many times can I divide n by 2 before reaching 1?"

Example:

n = 8

8 → 4 → 2 → 1
    1    2    3 divisions

Therefore:

log₂(8) = 3

This makes sense because:

2³ = 8


Another example:

n = 32

32 → 16 → 8 → 4 → 2 → 1

That takes 5 halvings.

Therefore:

log₂(32) = 5

because:

2⁵ = 32


BIG IDEA:

Whenever an algorithm repeatedly does:

n // 2

I should immediately start thinking:

"Probably log₂(n) levels."


============================================================
2. WHAT DOES THE HALVING FUNCTION ACTUALLY DO?
============================================================

Look carefully at:

return 2 * halving(n // 2) + 1

There is only ONE recursive function call:

halving(n // 2)

The "2 *" does NOT create two recursive calls.

It just multiplies the returned answer by 2.

So:

2 * halving(n // 2)

DOES NOT mean:

halving(n // 2) + halving(n // 2)


This distinction is extremely important.

The first version makes ONE recursive call.

The second version makes TWO recursive calls.

That completely changes the runtime.


============================================================
3. RECURSION TREE FOR THE ACTUAL FUNCTION
============================================================

Because there is only ONE recursive call, this isn't really a
branching tree. It is a skinny chain.


k = 0                  halving(n)
                           |
                           |
k = 1                halving(n/2)
                           |
                           |
k = 2                halving(n/4)
                           |
                           |
k = 3                halving(n/8)
                           |
                          ...
                           |
k = k                halving(n/2^k)
                           |
                          ...
                           |
k = log₂(n)           halving(1)
                       BASE CASE


At each level, n has been divided by another 2.

So:

k = 0:     n

k = 1:     n/2

k = 2:     n/4       = n/2²

k = 3:     n/8       = n/2³

...

k = k:     n/2^k


GENERAL RULE:

At depth k:

input size = n / 2^k


============================================================
4. HOW DO WE KNOW THE TREE HAS log₂(n) LEVELS?
============================================================

The recursion stops when the input reaches 1.

At level k:

n / 2^k = 1

Multiply both sides by 2^k:

n = 2^k

Now ask:

"What exponent k do I put on 2 to get n?"

That is EXACTLY what a logarithm tells us.

Therefore:

k = log₂(n)


So the recursion has approximately:

log₂(n) levels.


Example with n = 8:

k = 0              8
                   |
k = 1              4
                   |
k = 2              2
                   |
k = 3              1

log₂(8) = 3


============================================================
5. WHY IS THE RUNTIME Θ(log n)?
============================================================

Each level performs a small constant amount of work besides
the recursive call.

For example:

n <= 1       → constant work
n // 2       → constant work
2 * result   → constant work
+ 1          → constant work

We can represent this constant amount of work as:

c


Therefore the work looks like:

k = 0          c
k = 1          c
k = 2          c
k = 3          c
...
k = log₂(n)    c


There are approximately log₂(n) levels.

Each level does constant work.

Therefore:

total work ≈ c × log₂(n)

Constants disappear in asymptotic notation.

Therefore:

Θ(log n)


CORRECT ANSWER FOR THE QUIZ QUESTION:

Θ(log n)


============================================================
6. WHY ISN'T IT Θ(n log n)?
============================================================

I originally chose Θ(n log n).

The mistake is thinking that each of the log(n) levels is
doing n work.

It isn't.

There is only ONE function call at each level, and each call
does constant extra work.

So it is:

log(n) levels × constant work

NOT:

log(n) levels × n work


Therefore:

Θ(log n)


============================================================
7. WHAT WAS THE BRANCHING TREE ON THE WHITEBOARD?
============================================================

The professor's whiteboard also showed a tree like this:


k = 0                     n
                        /   \
                       /     \

k = 1                 n/2     n/2
                     /  \     /  \
                    /    \   /    \

k = 2              n/4  n/4 n/4  n/4

                   / \   / \ / \   / \

k = 3            n/8 n/8 ... ... n/8

                       ...

k = k        n/2^k  n/2^k ... n/2^k

                       ...

k = log₂(n)       1  1  1  1 ... 1


THIS represents a DIFFERENT kind of recursion.

It represents TWO recursive calls per function call.

For example:

return halving(n // 2) + halving(n // 2) + 1


That is fundamentally different from:

return 2 * halving(n // 2) + 1


============================================================
8. WHAT HAPPENS AT EACH LEVEL OF A TWO-BRANCH TREE?
============================================================

At:

k = 0

there is:

2⁰ = 1 node


At:

k = 1

there are:

2¹ = 2 nodes


At:

k = 2

there are:

2² = 4 nodes


At:

k = 3

there are:

2³ = 8 nodes


So in general:

At depth k:

NUMBER OF NODES = 2^k

INPUT SIZE OF EACH NODE = n / 2^k


This gives us:


DEPTH       INPUT PER NODE        NUMBER OF NODES

k = 0           n                     1 = 2⁰

k = 1          n/2                    2 = 2¹

k = 2          n/4                    4 = 2²

k = 3          n/8                    8 = 2³

...

k = k         n/2^k                  2^k

...

k = log₂(n)     1                 2^(log₂(n))


============================================================
9. TWO THINGS ARE HAPPENING AT THE SAME TIME
============================================================

As we move DOWN the tree:

The input size gets SMALLER:

n → n/2 → n/4 → n/8 → ...


But the number of nodes gets BIGGER:

1 → 2 → 4 → 8 → ...


So:

INPUT SIZE PER NODE:

n / 2^k


NUMBER OF NODES:

2^k


This is why we need to pay attention to BOTH:

1. How deep is the recursion?

2. How wide does the recursion tree become?


============================================================
10. WHAT DOES 2^k * c ON THE WHITEBOARD MEAN?
============================================================

Suppose every function call performs constant work:

c

At level k there are:

2^k nodes

Therefore the work at that level is:

2^k × c


Examples:

k = 0:

2⁰c = c


k = 1:

2¹c = 2c


k = 2:

2²c = 4c


k = 3:

2³c = 8c


So the amount of work per level grows like:

c, 2c, 4c, 8c, 16c, ...


============================================================
11. WHAT DOES THE SUM ON THE WHITEBOARD MEAN?
============================================================

The professor wrote something approximately like:

           log₂(n)
              Σ      2^k c
             k=0


Σ just means:

"Add all of these things together."


So this means:

Add the work from:

k = 0
through
k = log₂(n)


Which gives:

c(1 + 2 + 4 + 8 + ...)


The last level contains:

2^(log₂(n))

nodes.


============================================================
12. IMPORTANT LOG IDENTITY
============================================================

Remember:

2^(log₂(n)) = n


Why?

Because:

log₂(n)

literally means:

"What exponent do I put on 2 to get n?"


Example:

log₂(8) = 3

Therefore:

2^(log₂(8))

= 2³

= 8


Another:

log₂(32) = 5

Therefore:

2^(log₂(32))

= 2⁵

= 32


So:

2^(log₂(n)) = n


============================================================
13. WHY DOES THE TWO-BRANCH VERSION BECOME Θ(n)?
============================================================

The work across the levels looks like:

1 + 2 + 4 + 8 + ... + n

This is a geometric series.

The important beginner-friendly fact is:

When numbers repeatedly double like this, the final/largest
term is roughly the same size as all the previous terms
combined.

For example:

1 + 2 + 4 + 8 = 15

The largest term is 8.

15 is less than 2 × 8.

So asymptotically:

1 + 2 + 4 + ... + n = Θ(n)


Therefore the TWO-recursive-call version has:

Θ(n)

runtime.


============================================================
14. COMPARE THE TWO TREES
============================================================

ONE RECURSIVE CALL:

             n
             |
            n/2
             |
            n/4
             |
            n/8
             |
             .
             .
             .
             |
             1


Depth = log₂(n)

Width = always 1

Runtime = Θ(log n)


------------------------------------------------------------


TWO RECURSIVE CALLS:

                    n
                  /   \
                n/2   n/2
               / \     / \
             n/4 n/4 n/4 n/4
            / \  / \ / \  / \
           ...  ... ... ... ...
                 ...
          1 1 1 1 1 1 1 1 ...


Depth = log₂(n)

Width grows exponentially.

Number of calls at depth k = 2^k

Bottom level has approximately n calls.

Runtime = Θ(n)


============================================================
15. THE BIG IDEA
============================================================

When analyzing recursive algorithms, ask TWO separate
questions.


QUESTION 1:

HOW MUCH SMALLER DOES THE INPUT GET?

If:

n → n/2 → n/4 → n/8 → ...

then the depth is:

log₂(n)


QUESTION 2:

HOW MANY RECURSIVE CALLS DOES EACH FUNCTION MAKE?

One recursive call:

Skinny recursion tree.


Two recursive calls:

Branching recursion tree.


This can completely change the runtime even if both algorithms
divide n by 2.


============================================================
16. MEMORY SHORTCUT
============================================================

HALVING tells me how TALL the tree is.

BRANCHING tells me how WIDE the tree is.


If I repeatedly halve:

n → n/2 → n/4 → n/8 → 1

then:

HEIGHT = log₂(n)


But I still have to ask:

"How many recursive calls happen at every node?"


============================================================
17. MOST IMPORTANT DISTINCTION FROM THIS EXAMPLE
============================================================

This:

2 * halving(n // 2)

has ONE recursive call.


This:

halving(n // 2) + halving(n // 2)

has TWO recursive calls.


The first "2" is just multiplication.

The second example actually executes the function twice.


Therefore:


return 2 * halving(n // 2) + 1

           ONE CALL
              ↓
             n
             |
            n/2
             |
            n/4
             |
            ...
             |
             1

         Θ(log n)


VERSUS:


return halving(n // 2) + halving(n // 2) + 1

           TWO CALLS
              ↓
             n
           /   \
         n/2   n/2
        / \     / \
      n/4 n/4 n/4 n/4
           ...
      1 1 1 1 1 1 1 1

           Θ(n)

Today is about Dynamic Programming, Adam’s favorite topic 

What is an NP-complete problem? 

To prove a problem is NP-complete, it just has to check two boxes:

Easy to check (It's in NP): If someone hands you a completed answer, you can quickly double-check that it’s correct.

At least as hard as everything else in NP (It's NP-hard): It is among the toughest problems in that group. You prove this by showing: "If we could solve my problem fast, we could use that solution to solve another notoriously hard problem fast, too."



Layer 1: The "Budget" Trick (Turning Finding into Checking)
In real life, you usually want to find the best thing (e.g., "Find the cheapest flight"). That’s an optimization problem.
In theory, math people hate optimizing because it's messy. They prefer Yes/No questions:
Optimization: "Find the cheapest route."
Decision: "Is there a route that costs ≤ $500?" (This $500 is your budget).
Why make it a Yes/No question? Because if someone claims there is a route under $500, you just say, "Show me the ticket." You look at the ticket, add up the numbers, and verify it in seconds.

Layer 2: The Binary Search (How Yes/No Finds the Best Price)
How do you get back the cheapest route using only a Yes/No question? You play the High/Low game (Binary Search) with the budget:
"Is there a route under $1,000?" Yes. (Too high, cut in half).
"Is there a route under $500?" No. (Too low, try between $500 and $1,000).
"Is there a route under $750?" Yes.
Why won't this chop forever?
Computers can't store infinite decimals. They have finite bits (usually 64 bits). Even if you chopped continuous numbers in half over and over, you physically run out of precision after around 50 to 60 cuts. The computer literally cannot cut any smaller, so it stops.

Layer 3: What "NP-Hard" and the "Caller" Actually Mean
Your professor mentioned having a "solver" and "calling it a polynomial amount of times."
Think of an NP-Hard solver like a magical black box that answers an impossibly hard puzzle instantly.
Saying a problem is NP-Hard means: If you gave me that magical black box, I could solve every single problem in NP just by writing a simple loop around it.
You don't need to reinvent the wheel for every hard problem. If you crack one NP-Hard problem, you can route all the other hard problems through it with a few lines of code ("polynomial calls").
We call them hard because nobody on Earth has found a fast way to build that box without brute-forcing it.

Layer 4: The 3 Categories (In Plain English)
NP: Problems where checking the answer is easy. (If someone hands you a solved Sudoku, checking that each row has 1–9 is fast, even if solving it from scratch is painful).
NP-Hard: The master key problems. If you find a fast cheat to solve one, you can unlock all NP problems.
NP-Complete: The sweet spot. A problem that is both:
Easy to double-check once you have an answer (it's in NP).
A master key that could unlock everything else if solved fast (it's NP-Hard).

Layer 5: Picking Your Wikipedia Problem
For your assignment, do not pick an obscure math problem. Pick one that feels like a board game:
Subset Sum: You have a list of numbers. Can you pick a few that add up to exactly 100?
Vertex Cover: You have a web of hallways (graph). Can you place security guards at k corners so every single hallway is watched by at least one guard?
3-Coloring: Can you color a map using only 3 colors so no two touching countries have the same color?

Layer 1: What is Circuit-SAT?
Imagine a physical computer chip made of logic gates (AND, OR, NOT) with multiple input wires and a single output wire.
The question is simple: Is there any combination of inputs (True/False) that will make the final output wire light up (True)?
Checking is fast (O(n)): If someone gives you a specific set of inputs, you simply run the signals through each gate. It takes seconds to see if the final output equals 1. That puts it squarely in NP.
Solving is brutal: If there are k inputs, there are 2k combinations. Brute-forcing it takes exponential time.

Layer 2: Why Was It the Very First? (The Chicken-and-Egg Problem)
To prove a new problem is NP-hard, you usually show: "Problem A (already known to be NP-hard) reduces to Problem B."
The glaring problem in 1971: No problem was known to be NP-hard yet. There was no first domino to knock down.
Stephen Cook (and independently Leonid Levin) solved this by going straight to the metal. Every computer program running on a computer is fundamentally just an electrical circuit:
A deterministic computer running in polynomial time can only execute a polynomial number of steps.
Each step modifies memory bits using basic logic gates.
Therefore, the entire execution of any program that verifies an NP problem can be unrolled into a single, giant boolean circuit.

Layer 3: The Grand Takeaway (The Master Domino)
Because any problem in NP can be mechanically translated into an equivalent logic circuit, Circuit-SAT can simulate every single problem in NP.
If you built a magical black box that solved Circuit-SAT, you could pipe every verification algorithm on Earth into it and solve them all instantly. This made Circuit-SAT the foundational NP-complete problem that unlocked the rest of complexity theory.

Caching drops the time complexity from O(2ⁿ) to O(n²). Without it, the recursion recomputes subproblems exponentially. With caching, there are only n unique states (index). Each state iterates through at most n subsequent elements, doing O(1) cached lookups. Space complexity increases to O(n) to store subproblem answers in memory.



Here is the bottom-up formulation for the Longest Increasing Subsequence, followed by a direct breakdown of how bottom-up compares to top-down.

Bottom-Up Implementation of LIS
In the bottom-up approach, we eliminate recursion and the call stack by filling an array (or table) iteratively from the smallest subproblems to the largest.
(Note: You can also define dp[i] as the LIS ending at index i moving forwards 0 -> n-1. Both formulations solve the problem iteratively in O(n²) time and O(n) space).

Top-Down vs. Bottom-Up in General

Dimension
Top-Down (Memoization)
Bottom-Up (Tabulation)

Execution Flow
Starts at the original problem and branches downward recursively into subproblems as needed.
Starts at the trivial base cases and builds upward iteratively using loops.

Subproblem Evaluation
Lazy / On-demand: Computes only the subproblems reachable from the original call.
Eager: Computes every entry in the table/order, regardless of whether every state is needed.

Overhead
Incurs function call stack overhead and recursion limits (can hit RecursionError on large inputs).
Zero recursion overhead; uses simple loops and contiguous arrays.

Mental Model
Natural translation of the mathematical recurrence relation.
Requires figuring out a valid topological order / dependency direction beforehand.

Space Optimization
Generally requires storing all visited states in a hash map or cache table.
Often allows rolling arrays/variables to discard old states (e.g., keeping only the last row or two variables).

How to Choose Between Them
Use Top-Down when the state space is sparse (many possible subproblem states exist, but only a fraction are actually reachable), or when translating a tricky recursive decision tree quickly.
Use Bottom-Up when you need maximum performance, want to avoid call stack limits on large inputs, or intend to optimize auxiliary space by throwing away previously computed rows/values.

    """Returns the length of the longest strictly increasing subsequence."""
    if not seq:
        return 0
    answers = {}
    def longest_starting_at(index):
        if index not in answers:
            # We can always start a subsequence of length 1 using just seq[index].

            answers[index] = 1 + max(
                (longest_starting_at(j) for j in range(index + 1, len(seq)) if seq[j] > seq[index]),
                default=0,
            )
        return answers[index]
    return max(longest_starting_at(i) for i in range(len(seq)))

1. Edit Distance (Levenshtein Distance)
Problem Overview
Edit distance quantifies how dissimilar two strings are by calculating the minimum number of basic edit operations needed to transform one string into another.
Allowed Operations:
Insertion: Add a character.
Deletion: Remove a character.
Substitution / Transformation: Replace one character with another.
(Match / Copy carries zero cost).
Weighted Edit Distance: In generalized formulations, distinct operations carry variable cost weights (e.g., Costinsert, Costdelete, Costsub). The objective becomes finding the sequence of operations that yields the minimum total cost.

Example: Transforming "sunny" ↔ "snowy"
To transform "sunny" into "snowy":
s → s: Match / Copy (Cost: 0)
u → n: Substitute u with n
n → o: Substitute
n → w: Substitute
y → y: Match / Copy (Cost: 0)

Dynamic programming finds the global minimum alignment cost among all possible operation sequences.

Context & Warehouse Setup
Warehouse Layout: A 1D array of bins indexed 1 through n, arranged in strictly increasing order of book ISBN.
Base Station: Located at bin 0 (the negative direction relative to the bins).
Robot Behavior: To retrieve a book, DeNile searches its internal Binary Search Tree (BST) to locate the target bin, walks from the base station to the target bin, extracts the book, and returns to bin 0.

Parameters & Costs
f[1 … n]: Array of access frequencies, where f[i] is the request count for bin i.
α: Time cost per step between adjacent bins.
β: Time cost per internal tree comparison / node visit.
γ: Extraction time to retrieve a book from a bin.

Dynamic Programming Subproblem Formulation
Because the bins are sorted by ISBN, any valid search tree over a contiguous range of keys [i … j] forms a subtree. To minimize total retrieval time across all queries, we frame the optimal choice of the subtree root r (i ≤ r ≤ j) recursively.
Subproblem Definition: OptCost(i, j, …) represents the minimum search/traversal cost for the subset of keys from index i to j.
State Space:
i, j: The boundary indices of the current key subrange.
Additional state variables: Incoming direction or parent bin references.

A Minimum Spanning Tree (MST) is a way to connect every point in a network using the absolute shortest total path length without creating any loops. Kruskal's algorithm achieves this by sorting all available connections from cheapest to most expensive and repeatedly adding the lowest-cost link that doesn't form a circle until every point is connected. 

Loops are not allowed

LRU_CACHE #1
Of lru_cache: 
Essentially it creates a dictionary that maps the argument(s) used to the return value of the decorated function as called with those argument(s), then returns the return value. In future calls with the same argument(s) the cached return value is returned immediately and the decorated function is not called again.

If you call the decorator with a maxsize of None the cache will grow for each new discrete argument(s) in an unbounded fashion, eventually crashing with a MemoryError if enough unique calls are made. You shouldn’t usually use such an unbounded cache

If you call it without setting maxsize to None it also keeps track of how recently the wrapped function has been called with those particular argument(s), so there’s more memory overhead than just the return value. Using this information it acts as a Least Recently Used cache with an upper bounds of maxsize (that is by default 128 items). When the cache is full the oldest item on the cache (aka the least recently used) is discarded and the current argument(s) are added in its place.

In both cases the argument(s) must all be hashable, which is a limiting factor, and obviously it will only work if the decorated function is pure in the sense that it will always return the same value for the same argument(s) and has no other side effects. The maxsize value should usually be a power of 2 for the sake of efficiency as well.

You’re basically trading memory for speed, which means you probably should not use too many such caches, and only very rarely unbounded ones, but if your function is going to be called repeatedly with the same arguments, and especially if it’s most likely to be called often with the one of the most recent arguments, then it can be a huge speed boost with little overhead.
